🏛️ Class Diagrams

Class diagrams are the most common UML diagram type. They show the structure of classes, their attributes, methods, and how they relate to each other. Think of them as a blueprint for your object-oriented code.

What Class Diagrams Show

  • Classes: The main building blocks
  • Attributes: Data each class holds
  • Methods: Actions each class can perform
  • Relationships: How classes connect and depend on each other
  • Visibility: What is public, private, or protected

When to Use Class Diagrams

Use Class Diagrams for:

  • Design phase: Plan classes before you code
  • Large systems: Show how many classes fit together
  • Documentation: Explain the structure to new team members
  • Identifying patterns: Spot inheritance opportunities and design issues
  • API design: Show what's public vs. internal

Reading a Class Diagram

The Three-Part Class Box

Every class box is divided into three horizontal sections:

Example Class Box Structure


                ┌─────────────────────────────┐
                │ Dog                         │ ← 1. Class Name
                ├─────────────────────────────┤
                │ - name: string              │ ← 2. Attributes (data fields)
                │ - age: number               │    + public, - private, # protected
                │ - breed: string             │
                ├─────────────────────────────┤
                │ + getName(): string         │ ← 3. Methods (operations)
                │ + setAge(age: number): void │
                │ - calculateAge(): number    │
                └─────────────────────────────┘

Attributes: How to Read Them

Syntax Meaning Example
+ attribute: Type Public attribute + name: string
- attribute: Type Private attribute - id: number
# attribute: Type Protected attribute # internalId: string
attribute: Type = value With default value - count: number = 0
{static} attribute: Type Static (shared across all instances) {static} version: string

Methods: How to Read Them

Syntax Meaning Example
+ method(): ReturnType Public method + bark(): void
- method(): ReturnType Private method - validate(): boolean
+ method(param: Type): ReturnType Method with parameter + setName(name: string): void
+ method(p1, p2): Type Multiple parameters + create(name: string, age: number): Dog
{abstract} method(): Type Abstract method (must be implemented) {abstract} move(): void

Relationships Between Classes

Inheritance (Is-A)

When a class extends another, use a hollow triangle arrow pointing to the parent class.

classDiagram class Animal { - name: string + move() + sleep() } class Dog { - breed: string + bark() } class Cat { - color: string + meow() } Animal --|> Dog : extends Animal --|> Cat : extends

In code, this means Dog extends Animal and Cat extends Animal.

Association (Has-A)

When one class knows about or uses another, draw a solid arrow or line between them. Add multiplicity numbers to show how many.

classDiagram class Student { - id: number - name: string } class Course { - title: string - code: string } Student "*" -- "1..*" Course : enrolls in

This reads: "Many Students enroll in one or more Courses."

Composition (Strong Ownership)

When one class owns another and they have a strong life-cycle dependency, use a filled diamond. The contained object can't exist without the container.

classDiagram class House { - address: string } class Room { - number: string - size: number } House "1" *-- "1..*" Room : contains

This means: "A House is made up of one or more Rooms. Rooms don't exist without a House."

Aggregation (Weak Ownership)

When one class contains another but they can exist independently, use a hollow diamond.

classDiagram class Team { - name: string } class Player { - name: string - number: number } Team "1" o-- "*" Player : has

This means: "A Team has many Players, but Players can exist independently (they could join another team)."

Real Example: E-commerce System

classDiagram class User { - userId: number - name: string - email: string + register() + login() + logout() } class Order { - orderId: number - date: Date - total: number + calculateTotal() + addItem() + removeItem() } class Product { - productId: number - name: string - price: number + getDescription() + updatePrice() } class ShoppingCart { - items: Product[] + addProduct() + removeProduct() + getTotal() } User "1" -- "*" Order : places User "1" -- "1" ShoppingCart : owns ShoppingCart "*" -- "*" Product : contains Order "*" -- "*" Product : includes

What This Diagram Shows:

  • A User can place multiple Orders
  • Each User owns exactly one ShoppingCart
  • A ShoppingCart contains multiple Products
  • An Order can include multiple Products

Tips for Reading Class Diagrams

  • Start at the top: Read class names and attributes first
  • Follow the arrows: Understand relationships by tracing arrows
  • Check multiplicity: Look for numbers to understand "how many"
  • Check visibility: Notice which attributes and methods are public (+) vs. private (-)
  • Spot patterns: Look for inheritance hierarchies (triangles) vs. "has-a" relationships (diamonds)

Common Mistakes to Avoid

Mistake Problem Fix
Too many classes on one diagram Becomes hard to read Split into smaller focused diagrams
Missing multiplicity Unclear how many items are involved Add numbers like 1, *, or 1..*
Mixing different details Confuses the purpose Show either structure or behavior, not both
Forgetting visibility symbols API confusion Always mark +, -, or #
