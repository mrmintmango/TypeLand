⏱️ Sequence Diagrams

While class diagrams show what classes exist and their structure, sequence diagrams show how objects interact over time. They display the sequence of messages and method calls that happen during a specific scenario.

What Sequence Diagrams Show

  • Actors/Objects: The participants in the interaction
  • Messages: Method calls between objects
  • Order: The sequence of steps from top to bottom
  • Timing: Who calls whom and when
  • Return values: What comes back from calls

When to Use Sequence Diagrams

Use Sequence Diagrams for:

  • Showing workflows: How an order gets placed from start to finish
  • API interactions: How client and server communicate
  • Complex scenarios: Login, payment processing, multi-step procedures
  • Debugging flows: Understanding a confusing interaction
  • Requirements: Showing stakeholders what happens in a use case

Reading a Sequence Diagram

Anatomy of a Sequence Diagram

  • Top: Boxes representing actors or objects
  • Vertical dashed lines: "Lifelines" showing the lifetime of each object
  • Horizontal arrows: Messages or method calls
  • Numbers: The order in which messages happen

Read from top to bottom. Each arrow shows one step in the flow.

Types of Messages (Arrows)

Arrow Type Meaning Line Style When Used
Actor → Object Synchronous call (waits for response) Solid line with solid arrowhead Normal method calls (most common)
Object ← Object Return value (coming back) Dashed line with open arrowhead Showing what value is sent back
Object →→ Object Asynchronous call (doesn't wait) Solid line with half arrowhead Fire-and-forget, events, promises
Object → Object : self Self-call (calls own method) Arrow loops back to same object Internal processing

Example: Simple Purchase Flow

sequenceDiagram participant Customer participant ShoppingCart participant PaymentProcessor participant Database Customer->>ShoppingCart: addItem(product) ShoppingCart->>ShoppingCart: updateTotal() ShoppingCart-->>Customer: confirmed Customer->>ShoppingCart: checkout() ShoppingCart->>PaymentProcessor: processPayment(amount) PaymentProcessor->>PaymentProcessor: validateCard() PaymentProcessor-->>ShoppingCart: paymentApproved ShoppingCart->>Database: saveOrder(orderDetails) Database-->>ShoppingCart: orderSaved ShoppingCart-->>Customer: orderConfirmed

What This Diagram Shows:

  1. Customer adds an item to cart
  2. ShoppingCart updates its total internally
  3. ShoppingCart confirms to customer
  4. Customer checks out
  5. ShoppingCart calls PaymentProcessor to handle payment
  6. PaymentProcessor validates and approves
  7. ShoppingCart saves the order to database
  8. Database confirms save
  9. ShoppingCart confirms order to customer

Sequence with Loops and Conditions

Sequence diagrams can show conditional logic and repeated actions using special blocks.

sequenceDiagram participant User participant LoginService participant Database participant Logger User->>LoginService: login(username, password) alt username exists LoginService->>Database: getUser(username) Database-->>LoginService: user LoginService->>LoginService: validatePassword() alt password correct LoginService->>Logger: logEvent("Login successful") LoginService-->>User: authToken else password incorrect LoginService->>Logger: logEvent("Login failed") LoginService-->>User: error("Invalid password") end else username not found LoginService->>Logger: logEvent("User not found") LoginService-->>User: error("User does not exist") end

What You See Here:

  • alt block: Alternative paths (if/else)
  • Nested alt: Multiple conditions checked
  • Different outcomes: Based on conditions

Sequence with Parallel Processing

Use parallel blocks (par) to show actions happening at the same time.

sequenceDiagram participant Client participant API participant EmailService participant AnalyticsService Client->>API: registerUser(data) par send confirmation API->>EmailService: sendWelcomeEmail(email) and track event API->>AnalyticsService: trackEvent("user_registered") end API-->>Client: userCreated

What You See Here:

  • par block: Actions that can happen at the same time
  • The API sends an email AND records an event in parallel
  • Doesn't have to wait for one to finish before the other starts

How to Read Symbols and Notation

Symbol Meaning Example
: Separator between object name and lifeline User : UserController
methodName(param) Method call with parameter sendEmail(address)
methodName() : returnValue Show return value on arrow getUser() : User
*methodName() Repeated call (loop) *iterate(item)
loop { ... } Explicit loop block Run same sequence multiple times
alt { ... } else { ... } If/else conditional Different paths based on condition

Example: API Call with Error Handling

sequenceDiagram participant Browser participant Server participant Database participant ErrorLogger Browser->>Server: GET /user/123 Server->>Database: query(SELECT user WHERE id=123) alt user found Database-->>Server: user_record Server-->>Browser: 200 OK + user_data else user not found Database-->>Server: null Server->>ErrorLogger: log("User 123 not found") Server-->>Browser: 404 Not Found else database error Database-->>Server: error Server->>ErrorLogger: log("Database error") Server-->>Browser: 500 Server Error end

Lesson from This Diagram:

  • Show all possible outcomes
  • Include error paths, not just happy path
  • Demonstrate what gets logged

Tips for Reading and Creating Sequence Diagrams

  • Read top to bottom: Time flows downward
  • Follow the arrows: Each arrow is one step
  • Check dashed vs. solid: Dashed = return, Solid = call
  • Look for blocks: alt, par, loop, etc. show special logic
  • Count the steps: Make sure the order makes sense
  • Include error cases: Don't just show the happy path

Sequence vs. Class Diagrams

Aspect Class Diagram Sequence Diagram
Shows Structure (what exists) Behavior (what happens)
Time dimension No time Top to bottom = time
Use for Design before coding Explain workflows or trace bugs
Focus Classes and relationships Objects and interactions
Best audience Developers, architects Everyone (easier to follow)
