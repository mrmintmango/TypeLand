📊 UML Diagrams and Syntax

UML (Unified Modeling Language) is a visual way to design and communicate software structure before you build it. Instead of describing everything in words, you draw boxes, lines, and arrows to show how classes, objects, and systems connect and interact.

Why UML Matters

  • Plan before code: Sketch your design visually
  • Communicate clearly: Show teammates and stakeholders how the system works
  • Catch design problems early: Fix issues on paper, not in code
  • Document structure: Keep a record of your architecture

Common UML Diagram Types

Types of UML Diagrams

UML includes many diagram types. Here are the most useful for software design:

Diagram Type Purpose Best For
Class Diagram Show classes, attributes, methods, and relationships Object-oriented design
Sequence Diagram Show how objects communicate over time Interaction and flow
Use Case Diagram Show actors and what they do in the system Requirements and scope
State Diagram Show states and transitions Complex state machines

UML Boxes and Notation

Class Box Anatomy

A class in UML is drawn as a box divided into three sections: 


                ┌─────────────────────────────┐
                │ Dog                         │ ← 1. Class Name
                ├─────────────────────────────┤
                │ - name: string              │ ← 2. Attributes (data fields)
                │ - age: number               │    + public, - private, # protected
                │ - breed: string             │
                ├─────────────────────────────┤
                │ + getName(): string         │ ← 3. Methods (operations)
                │ + setAge(age: number): void │
                │ - calculateAge(): number    │
                └─────────────────────────────┘

Visibility Symbols

Symbol Meaning Example
+ Public (visible to all) + getName(): string
- Private (hidden inside) - id: number
# Protected (visible to subclasses) # validate(): boolean
~ Package (visible in package) ~ helper(): void

Relationships and Arrows

Main Arrow Types

Association: One class knows about another

Student ———→ Course
Solid line: a Student has a relationship with Course

Inheritance (Generalization): One class extends another

Animal ←|——— Dog
Hollow triangle: Dog extends/is-a Animal

Implementation: Class implements an interface

Drawable ←|····· Circle
Hollow triangle + dashed line: Circle implements Drawable

Composition: Strong "has-a" relationship (part of)

House ◆——— Room
Filled diamond: House owns Rooms; Room can't exist without House

Aggregation: Weak "has-a" relationship (contains)

Team ◇——— Player
Hollow diamond: Team has Players; Players can exist without Team

Dependency: One class uses another temporarily

Logger ····→ File
Dashed line: Logger temporarily uses File

Multiplicity (How Many?)

Numbers on arrows show how many instances are involved in a relationship.

Notation Meaning Example
1 Exactly one One Student has one StudentID
0..1 Zero or one A Student may have zero or one Scholarship
* or 0..* Zero or more A Course has zero or more Students
1..* One or more A Team has one or more Players
2..5 Between two and five A Car has 2-5 Doors

Example with Multiplicity

Teacher ————— 1..* Student

This reads as: "One Teacher is associated with one or more Students"

Quick Reference: Arrow Legend

Arrow Type Meaning Line Style Use When
Solid with arrowhead Association Solid line Showing a regular relationship
Hollow triangle Inheritance Solid line One class extends another
Hollow triangle (dashed) Implementation Dashed line Class implements interface
Filled diamond Composition Solid line Strong ownership
Hollow diamond Aggregation Solid line Weak ownership
Dashed arrow Dependency Dashed line Temporary use
